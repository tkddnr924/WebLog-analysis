# 0002. 데스크톱 앱 구조(3단계)

상태: 채택(2026-09-08).

## 1. 세 층 분리

- `weblog-engine`(파서·저장소) ← `weblog-service`(프로젝트 상태, 백그라운드 가져오기, 취소, 진행 이벤트 빈도 제한, 읽기 연결 풀, 무거운 조회 직렬화) ← `apps/desktop/src-tauri`(명령 등록·입력 검증·응답 변환만).
- 서비스 계층은 Tauri에 의존하지 않아 `cargo test`만으로 흐름(열기 → 탐색 → 가져오기 → 취소 → 재개 → 조회 → 상세)을 검증한다. Tauri 계층은 얇아서 별도 테스트 없이 컴파일과 실제 실행으로 확인한다.
- 대안: 명령 안에서 엔진을 직접 호출. 취소·진행·동시성 규칙이 명령마다 흩어지므로 채택하지 않았다.

## 2. 쓰기 연결 하나 + 읽기 연결 풀

- 가져오기 스레드가 `Store`의 Mutex를 실행 내내 잡는다. 그동안 조회·작업 목록은 미리 만들어 둔 읽기 연결(`Reader`, 기본 2개)로 처리한다. `LogQuery` 트레이트가 페이지·건수·상세·작업 메타데이터 조회를 `Store`와 `Reader`에 같은 구현으로 제공한다.
- 활성화·삭제·검증·프로젝트 전환 같은 쓰기 작업은 가져오기 중이면 `ImportRunning` 오류로 거부한다(try_lock).
- 무거운 조회(전체 건수, 분포)는 별도 잠금으로 동시 1개로 제한한다. 설계 문서의 "초기 1개" 실험값을 그대로 둔다.

## 3. 진행 통지: 이벤트 + 폴링

- 서비스가 배치 커밋마다 진행 스냅샷을 갱신하고 250ms 이상 간격으로만 이벤트(`weblog://import`)를 보낸다. 종료 통지는 항상 보낸다.
- UI는 이벤트를 구독하면서 2초 폴링(`import_status`)으로 유실을 보완한다. `import_status`는 종료 통지를 한 번만 돌려주고 기록을 정리한다.
- 새 가져오기의 작업 ID는 첫 배치 커밋(또는 그 전 실패) 시점에 확정되어 `start_import`가 그 값을 돌려준다. 파일이 없어 작업이 만들어지지 않으면 오류로 돌려준다.

## 4. IPC 규약

- 명령 인자는 `#[tauri::command(rename_all = "snake_case")]`, 구조체는 `#[serde(rename_all = "snake_case")]`로 고정한다. TypeScript 타입(`src/types.ts`)은 snake_case 필드를 그대로 쓴다. Tauri의 camelCase 자동 변환에 기대지 않는다.
- 오류는 `ServiceError`를 문자열로 직렬화한다. 메시지에 입력 원문은 들어가지 않는다.
- 권한(`capabilities/default.json`)은 `core:default`, 이벤트 listen/unlisten, 파일·폴더 선택 대화상자만 허용한다. 파일 읽기·쓰기 권한은 주지 않는다. 경로는 명령 인자로 넘기고 Rust가 연다.

## 5. 조회 화면

- 커서 기반 추가 로드(페이지 300행), 가상 스크롤(`@tanstack/react-virtual`), UI 캐시 8MiB 상한(앞쪽 행을 버리고 버린 수를 표시), 요청 식별자로 오래된 응답 폐기(`src/lib/pages.ts`, 테스트 있음).
- 전체 건수는 별도 버튼이며 조회 조건마다 다시 세야 한다.
- 상세는 구조화 필드와 "재구성 로그" 탭으로 나뉘고, 재구성 탭은 원문이 아님을 항상 표시한다. 로그 값은 React 텍스트 노드로만 렌더링한다.

## 6. 디자인 선택

- 차가운 회색 바탕 + 단일 강조색(짙은 청록), 상태코드 계열에만 의미색. 데이터 값(IP·경로·UA)은 고정폭. 본문 글꼴은 사용자가 지정한 JayeonSans(Regular·Medium woff2를 `src/assets/fonts/`에 번들, 2026-09-08)이며 시스템 글꼴 스택(Segoe UI / 맑은 고딕 / Apple SD Gothic Neo)을 대체 글꼴로 둔다. 외부 폰트 요청은 없다.
- 진행 표시는 전체 줄 수를 세지 않으므로 비율 대신 확정 건수를 보여준다.
- (2026-09-08 개정) 처음에는 왼쪽 단계 레일(파일 → 포맷 → 가져오기 → 조회 → 통계)로 다섯 화면을 나눴으나, 사용자 검토에서 입력 폼과 편집기가 기본으로 펼쳐져 부담스럽다는 결론이 나 세 화면으로 줄였다. 시작(서버 종류 + 폴더 선택 → 파일 목록 → 첫 레코드 한 줄의 원문·파싱 결과로 포맷 확인) → 파싱 중 → 결과(조회·통계·작업 탭). 포맷 확인은 샘플 한 줄을 조각(공백 기준, "…"·[…]는 한 조각; 또는 | , ; 탭 구분)으로 나눠 조각마다 뜻 라벨(시간·IP·상태코드…·무시)을 붙이는 퍼즐 방식이다(`src/lib/puzzle.ts`, 테스트 있음). 라벨은 select 또는 드래그 앤 드롭으로 바꾸며, 바꿀 때마다 블록 정의를 만들어 `preview_format`으로 다시 판별한다. 템플릿 목록은 서버 종류로 거른다(Apache/Nginx: common·combined, IIS: W3C만). 블록 목록·YAML 편집기(0003)는 사용자 검토에서 화면에서 제거했다. 엔진·CLI의 프로필 정의·검증·YAML 변환 기능은 그대로 남아 있고, 앱은 퍼즐이 만든 정의만 쓴다. Windows WebView2에서 HTML5 드래그 앤 드롭이 동작하도록 창 설정 `dragDropEnabled: false`를 둔다(OS 파일 드롭은 쓰지 않는다). 원문 한 줄을 보여주기 위해 `sample_lines` 명령을 추가했으며, 줄 수·바이트 상한이 있고 저장·로그 기록에 쓰지 않는다(샘플은 미리보기 동안만 화면에 남는다).
- 도구 종류상 `design-taste-frontend` 스킬의 랜딩 페이지 규칙은 적용 대상이 아니며, `frontend-design`의 기본값 회피(카드 나열, 장식용 그라디언트, 대문자 라벨)를 따랐다. 다크 모드는 이번 범위에 넣지 않았다.

## 7. 도구 버전 제약

- typescript-eslint 8.69는 TypeScript 7.0을 지원하지 않아 TypeScript 6.0.3으로 고정했다.
- `react-hooks/set-state-in-effect` 규칙은 IPC 호출 뒤 setState하는 마운트 시 불러오기 패턴을 동기 setState로 오인하므로 끄고 이유를 설정 파일에 적었다.
