# WebLog 개발 하네스 설계

상태: 사용자 합의 반영 완료.

## 1. 확정 사항

확정 사항:
- 핵심 개발 언어 Rust, 데스크톱 프레임워크 Tauri.
- 서버 유형 선택 → 경로 입력 → 재귀 파일 탐색 → 포맷 검사·수정 → 파싱 → DB 저장.
- Apache / Nginx / IIS / Unknown 구분 및 사용자 정의 포맷 지원.
- 퍼즐형 포맷 편집과 YAML처럼 구조화된 결과 뷰 제공.
- 설치된 스킬: find-skills, rust-best-practices, rust-async-patterns, rust-testing, tauri-v2.
- UI 디자인 스킬: web-design-guidelines, frontend-design, design-taste-frontend.
- 입력은 100GB 이상일 수 있다. 전체 데이터를 메모리에 적재하지 않고 디스크 영속 저장과 쿼리 기반 조회를 사용한다.
- 사용자 환경: Windows 가상 인스턴스, 일반적인 RAM 16GB, 입력 규모는 압축 후 100GB 이상. HDD 80GB 이상은 현재 전체 디스크 용량이며 필요에 따라 증설 가능하다. 80GB를 분석 공간의 고정 상한으로 취급하지 않는다.

추가 확정 사항:
- Rust + Tauri 2 + React·TypeScript + 영속 DuckDB. Windows x64를 최초 지원한다.
- 원문은 DB·별도 아카이브에 복제하지 않는다. 파싱 필드, 출처 파일, 줄/레코드 위치를 저장한다.
- 필드 조합 결과는 재구성 로그로 표시한다. 원본 바이트의 정확한 복원을 보장하지 않는다.
- 여러 사용자 동시 접속은 최초 범위에서 제외한다.
- 최초 지원 로그: Apache/Nginx 접근 로그, IIS W3C, 커스텀 단일행 텍스트.
- 파일 가져오기 중심으로 시작. 실시간 감시와 에러 로그의 멀티라인 처리는 후속 범위.
- 일반 텍스트와 gzip 지원. gzip 재개는 처음부터 재생하며 이미 커밋한 레코드를 건너뛰는 방식부터 시작.
- 처리량·메모리·조회 지연은 Windows·RAM 16GB·HDD 기준 선행 실험으로 측정하고 기록한다. 임의 성능 수치 확정 때문에 구현을 중단하지 않는다.

## 3. 에이전트 작업 규칙

- 변경 전에 관련 코드·문서·테스트와 적용되는 스킬을 확인한다.
- 이미 합의한 범위의 구현·수정·검증은 반복 확인 없이 진행한다.
- 확정된 DB·UI 기술·지원 범위를 반복 확인하지 않는다. 변경이 필요하면 근거와 영향을 제안한다.
- 일상적인 모듈 분리·명명·오류 처리 방식은 합의한 설계 안에서 판단한다.
- 불명확한 요구는 가정을 명시한다. 결과에 큰 영향을 주는 경우 구체적인 선택지를 제안한다.
- 요청 범위 밖 리팩터링과 신규 의존성 도입을 최소화하고, 필요한 의존성은 이유를 기록한다.
- 새 스킬 설치·업데이트는 사용자 선택 후 수행한다. 설치된 스킬 원문을 임의로 수정하지 않는다.
- 사용자가 요청하지 않으면 하위 에이전트를 생성하지 않는다.
- 완료 보고에는 변경 내용, 실행한 검사, 남은 제한을 포함한다. 미실행 검사를 통과로 표시하지 않는다.
- 대화·설계 문서는 한국어, 코드 식별자는 영어를 기본으로 한다.

## 4. 스킬 적용 및 보완 규칙

- Rust 코드 작성·검토: rust-best-practices.
- 비동기 작업·채널·취소·동시성: rust-async-patterns.
- Rust 테스트·성능 검증: rust-testing.
- Tauri 명령·상태·권한·패키징: tauri-v2.
- 새 기술에 맞는 스킬 탐색: find-skills.
- UI 가이드라인 검토: web-design-guidelines.
- 프런트엔드·시각 디자인: frontend-design, design-taste-frontend.

스킬 예시를 프로젝트 요구와 무관하게 복사하지 않는다. 다음 보완 규칙을 적용한다.
- tauri-v2의 모든 로직을 lib.rs에 두라는 표현은 적용하지 않는다. lib.rs는 조립·등록을 담당하고 핵심 로직은 별도 모듈/crate에 둔다.
- 스킬 예시의 unwrap/expect를 제품 코드에 복사하지 않는다. 외부 입력과 I/O 실패는 Result로 처리한다.
- IPC 구조체는 serde 속성으로 직렬화 규약을 명시한다. 중첩 필드의 이름이 자동 변환된다고 가정하지 않는다.
- TDD는 파서·데이터 무결성·버그 수정에 우선 적용한다. 문서·단순 스타일 변경에 무의미한 테스트를 요구하지 않는다.
- 스킬의 80~100% 커버리지 목표는 참고 지표로 사용하고 초기 일괄 통과 기준으로 강제하지 않는다. 중요 실패 시나리오의 검증 여부로 판단한다.
- 예제의 라이브러리 버전과 API는 도입 시 공식 문서와 실제 빌드로 검증한다.

## 5. 아키텍처 규칙

의존 방향: UI → Tauri 명령 계층 → 애플리케이션 서비스 → 파서·저장소.

- 파서와 데이터 모델은 Tauri에 의존하지 않는다. GUI 없이 테스트할 수 있어야 한다.
- Tauri 명령 계층은 입력 검증, 서비스 호출, 응답 변환을 맡는다.
- 파일 탐색·파싱·DB 접근은 Rust에서 수행한다. UI는 입력과 표시를 담당한다.
- 스캔, 포맷, 파서, 가져오기 작업, 저장소, 조회를 모듈로 분리한다. 처음부터 모듈마다 crate를 만들 필요는 없다.
- 파일 전체 읽기, CPU 파싱, 동기 DB 작업으로 UI 스레드와 비동기 실행기를 막지 않는다.
- 동시 작업 수와 큐 크기에 상한을 둔다. 소비가 늦으면 생산 속도를 제한한다.
- 취소는 협력적으로 처리한다. 이미 시작한 blocking 작업이 즉시 중단된다고 가정하지 않는다.
- 진행 이벤트에는 job_id를 포함하고 전송 빈도를 제한한다. UI 재연결 시 현재 상태를 조회할 수 있어야 한다.

## 6. 파일 탐색과 포맷 판별 규칙

- 서버 종류와 실제 로그 포맷을 분리한다. 서버 Unknown이어도 포맷이 확인되면 파싱할 수 있다.
- 파일명 패턴은 후보 선정에만 사용한다. 포맷은 내용으로 검사한다.
- 사용자가 선택한 경로 아래를 재귀 탐색하고 포함·제외 패턴과 선택 파일 목록을 제공한다.
- 심볼릭 링크는 기본적으로 따라가지 않는다. 권한 오류는 해당 파일·디렉터리 오류로 보고한다.
- 파일별로 포맷을 검사한 후 동일 포맷끼리 그룹화한다. 폴더 전체에 하나를 강제하지 않는다.
- 샘플 줄 수와 읽기 크기에 상한을 두고 후보, 검사 건수, 매칭률, 실패 예시를 표시한다.
- 샘플 매칭률을 서버 식별 확률이나 전체 파일 정확도로 표현하지 않는다.
- IIS W3C는 #Fields 헤더와 헤더 변경을 반영한다. 주석·헤더를 실패 로그로 집계하지 않는다.
- 인코딩 오류, CRLF/LF, BOM, 빈 줄, 매우 긴 줄의 처리 정책을 명시한다. 손실 변환을 숨기지 않는다.
- 입력 파일이 가져오는 중 변경된 경우 이를 감지하고 중단·재검사한다. 최초 버전은 고정된 파일 가져오기를 기준으로 한다.

## 7. 퍼즐·YAML·정규표현식 규칙

- 버전이 있는 구조화된 포맷 정의를 유일한 기준으로 삼는다.
- 퍼즐과 YAML은 같은 정의를 편집하고, Rust 엔진이 검증·실행한다.
- 미리보기와 실제 가져오기는 동일한 파서와 정규화 로직을 사용한다.
- 필드명, 타입, 필수 여부, 구분자, 누락값, 날짜 형식과 시간대를 정의할 수 있어야 한다.
- 원문 구간 추출과 타입·범위 검증을 분리한다. 정규식 매칭만 성공했다고 유효한 IP·날짜로 간주하지 않는다.
- 정규식은 포맷별로 컴파일하고 재사용한다. 패턴 크기, 입력 길이, 샘플 수에 한도를 둔다.
- 고급 정규표현식은 별도 블록으로 유지한다. 임의 정규식을 항상 퍼즐로 역변환할 수 있다고 약속하지 않는다.
- 잘못된 YAML이나 포맷 정의는 적용하지 않고 마지막 유효 버전을 유지한다.
- 편집 내용과 적용된 포맷 버전을 구분한다. 포맷 변경만으로 기존 파싱 결과를 덮어쓰지 않는다.
- 사용자 정의 필드는 고정 필드와 충돌하지 않는 확장 영역에 보존한다.

## 8. 정규화와 데이터 보존 규칙

- 결과에 source_id, 파일 내 줄/레코드 위치, import_job_id, parser_profile_version을 연결한다.
- 파싱 필드와 원본 파일·위치를 연결한다. 입력 파일을 수정하거나 원문을 복제 저장하지 않는다.
- 시간은 UTC로 정규화하고 사용한 시간대 정보를 보존한다. 시간대가 없으면 명시적으로 지정받거나 미확정으로 남긴다.
- IP·URL·User-Agent·사용자 문자열을 손실 변환하지 않는다. URL 디코딩 값은 필요하면 별도 파생 필드로 둔다.
- 상태코드, 전송량, 시간 단위의 타입과 범위를 명시한다. 누락값을 0으로 임의 변환하지 않는다.
- 파싱 실패는 출처, 위치, 오류 코드, 입력 내용이 포함되지 않은 설명으로 추적한다. 실패 원문도 저장하지 않는다. 저장 한도에 도달하면 조용히 버리지 않고 작업을 중단·보고한다.
- 빈 줄·주석 등의 제외 사유와 건수를 집계한다.

## 9. 저장과 작업 상태 규칙

- DB 접근은 저장소 계층에 모은다. UI에 DB 연결이나 임의 SQL 실행 권한을 노출하지 않는다.
- 값은 바인딩하고 동적 정렬·컬럼 이름은 허용 목록으로 제한한다.
- DB 스키마 변경은 버전이 있는 마이그레이션으로 수행한다.
- 성공·실패 레코드와 체크포인트는 같은 배치 트랜잭션에서 확정한다.
- 동일 파일의 동일한 가져오기 작업을 재시도하면 중복 행이 생기지 않아야 한다.
- 서로 다른 위치에 같은 원문이 반복됐다고 로그를 제거하지 않는다. 내용 해시만으로 행을 중복 판정하지 않는다.
- 파일 식별 정책은 경로 외에 내용 검증을 포함한다. 크기·수정 시각은 빠른 후보 판정에만 사용한다.
- 포맷 변경에 따른 재파싱은 새 결과 버전으로 취급한다. 완료 후 결과 전환을 명시적으로 처리한다.
- 디스크 부족·DB 오류가 발생하면 해당 미커밋 배치를 롤백하고 실패 상태를 보고한다.
- 작업 상태는 queued → running → completed/completed_with_errors 또는 cancelling → cancelled, 오류 시 failed로 구분한다.
- 취소 시 미커밋 배치는 롤백하고 커밋 완료분은 유지한다. 부분 결과임을 화면에 표시한다.
- 비정상 종료된 running 작업은 다음 실행에서 interrupted로 식별한다. 재개 전 파일과 포맷 버전을 검증한다.
- DuckDB는 앱의 단일 소유 프로세스에서 DB 연결을 관리하고, 단일 가져오기 쓰기 큐와 제한된 조회 연결을 사용한다. 기록과 체크포인트는 동일 DB 트랜잭션으로 처리한다.

## 10. 뷰어와 앱 경계 규칙

- 로그 테이블, 재구성 로그, 구조화 트리는 같은 선택 레코드를 표시한다. 재구성 로그를 원문이라고 부르지 않는다.
- 조회는 페이지 단위로 수행하고 테이블은 가상 스크롤을 사용한다. 전체 결과를 UI로 전송하지 않는다.
- 필터·정렬은 Rust/DB에서 처리한다. 안정적인 보조 정렬 키로 페이지 간 중복·누락을 방지한다.
- 오래된 검색 응답이 최신 필터 결과를 덮어쓰지 않도록 요청을 식별한다.
- 퍼즐 편집은 마우스 외에 키보드로도 수행할 수 있어야 한다.
- 로그 문자열은 텍스트로 표시한다. HTML·스크립트로 실행하지 않는다.
- 원본 로그를 진단 로그나 테스트 저장소에 무단 포함하지 않는다. 기본 동작은 로컬 처리다.
- Tauri 권한은 필요한 기능과 경로 범위로 제한하고 명령 인자도 Rust에서 검증한다.

## 11. 검사와 완료 기준

프로젝트를 구성한 뒤 scripts/check를 아래 검사들의 공통 진입점으로 만든다. 아직 없는 명령을 실행 완료로 보고하지 않는다.

- Rust: cargo fmt --all -- --check
- Rust: cargo clippy --workspace --all-targets --locked -- -D warnings
- Rust: cargo test --workspace --locked
- 선택된 UI 기술의 타입 검사, 린트, 관련 테스트, 프로덕션 빌드.
- --all-features는 기능 조합의 호환성이 확인된 경우에만 사용한다. 그 외 지원 조합별로 검사한다.
- Rust 도구체인과 의존성 잠금 파일을 관리하고 로컬·CI에서 같은 검사 진입점을 쓴다.
- 지원 운영체제별 Tauri 빌드 검증을 둔다. 브라우저 UI 검사로 네이티브 연동 검사까지 대체하지 않는다.
- 변경 범위와 관련된 검사를 먼저 실행한다. 통과 후 새 근거 없이 같은 검사를 반복하지 않는다.

필수 동작 검증:
- 지원 포맷별 입력 → 예상 필드 비교와 미리보기/실제 결과 일치.
- Unknown·커스텀 포맷, 혼합 파일, IIS #Fields 변경.
- IPv6, 시간대, 누락값, 깨진 입력, 긴 줄, 인코딩 오류.
- 서로 다른 위치의 반복 로그 보존, 원문 미저장, 재구성 표시, 동일 작업 재시도 중복 방지, 포맷 버전별 재파싱.
- 취소·비정상 종료·파일 변경·DB 오류 이후 체크포인트와 부분 결과의 일관성.
- 대표 데이터의 release 빌드 처리량, 최대 메모리, DB 크기, 조회 지연 기록.

성능 목표값은 대표 데이터와 대상 장비를 정한 뒤 기준 측정으로 합의한다. 임의의 처리량을 보장하지 않는다.

## 12. 권장 개발 순서

1. 확정 문서 확인 및 도구체인·검사 진입점 구성. 저장·조회 선행 실험을 UI보다 먼저 수행.
2. 합성 로그와 포맷 정의, GUI 독립 Rust 파서 구현.
3. 파일 탐색·샘플 검사·포맷 미리보기 구현.
4. 배치 저장·작업 상태·취소·재실행 검증.
5. 기본 조회 테이블·재구성 로그·구조화 뷰 연결.
6. 퍼즐 편집기·YAML 왕복 변환·사용자 프리셋 구현.
7. 대표 대용량 검증·지원 OS 빌드·배포 패키징.

기술 스택·최초 로그 범위·스킬 보완 규칙은 합의되었다. 기준 환경은 Windows·RAM 16GB·증설 가능한 HDD이며 입력은 압축 후 100GB 이상이다.

## 13. 100GB 이상 저장·조회 설계 보완

### 권장 저장 구성

- 초기 구현은 프로젝트별 영속 DuckDB 하나에 분석 로그와 작업 메타데이터를 저장한다.
- logs: 시간, IP, 요청, 상태코드 등 타입이 지정된 분석 컬럼과 출처·버전 식별자.
- 원문 테이블을 만들지 않는다. sources에 경로·인코딩·압축·파일 식별 정보를 저장하고 행에는 source_id와 위치만 연결한다.
- parse_errors: 출처·위치·오류 코드·입력 문자열을 포함하지 않은 설명. 실패한 행은 필드 재구성이 불가능할 수 있으므로 위치만 표시한다.
- import_jobs/import_batches/sources/parser_profiles: 작업 진행, 배치 확정 정보, 파일 식별, 포맷 스냅샷.
- summaries: 필요 시 완료 배치에 대응하는 시간대별 요청량·상태코드 통계. 원본에서 재생성 가능하게 한다.
- SQLite와 DuckDB에 같은 체크포인트를 이중 기록하지 않는다. 초기에는 여러 DB 간 원자성 문제를 피한다.
- Parquet는 후속 아카이브·공유 옵션으로 둔다. 100GB라는 이유만으로 초기 저장소를 분산 파일 구조로 복잡하게 만들지 않는다.
- 저장 대상은 로컬 디스크를 기본으로 한다. 임시 쿼리 공간도 사용자가 용량을 확인할 수 있는 로컬 경로에 둔다.

### 가져오기 흐름

1. 입력 파일 크기, 압축 여부, 샘플의 원문·정규화 크기를 확인해 저장 공간을 추정한다. 압축 해제 크기를 모르면 추정치로 표시한다.
2. 파일을 순차적으로 읽고 필요하면 스트리밍 압축 해제한다. 원문은 파싱 동안만 제한된 버퍼로 다루고 논리 레코드 위치를 저장한다.
3. Rust 파서가 제한된 배치로 정규화한다. 행 수 외에 바이트 수에도 상한을 둔다.
4. DB 쓰기 작업이 같은 트랜잭션 안에서 분석 컬럼, 출처 위치, 오류, 배치 완료 정보, 체크포인트를 기록한다. Appender 등 배치 적재 API를 검토한다.
5. 커밋 성공 후에만 저장 완료 건수와 조회 가능한 배치를 갱신한다. 읽은 건수와 저장한 건수를 구분한다.
6. 완료된 배치는 조회할 수 있게 하되 전체 작업 완료와 부분 결과를 구분한다.
7. 재시작은 마지막 확정 배치 다음부터 수행한다. 일반 파일은 검증된 바이트 오프셋, gzip은 초기 버전에 한해 재생·건너뛰기를 사용한다.

행마다 INSERT/COMMIT하지 않는다. 배치 ID로 재시도를 식별하고, 동일 원문이 여러 번 나타난 정상 레코드는 모두 보존한다.

### 앱 실행과 조회 흐름

1. 앱 실행 시 스키마와 메타데이터만 읽고 전체 로그를 읽거나 전체 COUNT를 수행하지 않는다.
2. UI가 데이터셋, 시간 범위, 조건, 정렬, 페이지 크기를 포함한 구조화된 요청을 보낸다.
3. Rust가 요청을 검증하고 파라미터 바인딩 SQL을 실행한다. UI가 입력 SQL을 임의 실행하는 기능은 초기 범위에 넣지 않는다.
4. 기본 시간 정렬에서는 시간과 고유 레코드 키를 커서로 쓰고, 마지막 행 이후의 다음 페이지를 조회한다. NULL 시간은 별도 규칙으로 다룬다.
5. 페이지 크기와 응답 바이트 크기에 상한을 두고 화면에는 필요한 컬럼만 전송한다. 초기 실험값은 200~500행이며 확정 성능 목표가 아니다.
6. 긴 User-Agent·확장 필드 전체는 상세 화면에서 별도로 조회하고 저장 필드와 포맷 버전으로 재구성 로그를 만든다. UI 캐시는 페이지 수뿐 아니라 바이트 크기로 제한한다.
7. 내보내기는 쿼리 결과를 디스크로 스트리밍한다. 전체 결과를 Vec이나 UI 상태로 모으지 않는다.

큰 OFFSET을 기본 페이지 이동 방식으로 사용하지 않는다. 커서만으로 쿼리가 빨라진다고 가정하지 않고 실행 계획을 검증한다. 페이지 이동 중 가져오기가 진행되면 확정 배치 범위와 결과 버전을 커서에 고정한다. 재파싱으로 버전이 바뀌면 기존 커서를 무효화한다.

### 쿼리 비용 관리

- 기본 화면에 시간 범위를 제공하고 자주 쓰는 타입 컬럼을 직접 필터링한다.
- 시간 기준 데이터 배치를 유지하고 배치 내부 정렬의 효과를 측정한다. 100GB 전체를 메모리에서 정렬하지 않는다.
- 범위를 크게 확장한 통계·정규식 검색·임의 정렬은 취소 가능한 작업으로 수행한다.
- LIMIT은 반환 행 수 제한이다. 스캔·정렬량까지 제한한다고 가정하지 않는다.
- 페이지 조회 때마다 필터 전체 건수를 계산하지 않는다. 다음 페이지 유무를 우선 표시하고 정확한 건수는 별도 요청으로 계산한다.
- 문자열 전체 정규식 검색에는 광범위한 스캔이 필요할 수 있다. 반복 검색이 핵심이면 추후 전문 검색 인덱스를 별도로 검토한다.
- 요약 통계는 배치 범위와 버전을 표시하고, 필터가 요약 차원을 벗어나면 실제 로그를 조회한다.

### 자원·디스크 관리

- 압축 후 100GB를 압축 해제 후 100GB로 계산하지 않는다. 실제 확장 비율과 정규화 크기를 샘플로 추정하되 보장값으로 표시하지 않는다.
- 전체 로그 가져오기를 기본 권장 흐름으로 둔다. 저장 공간 추정은 용량 증설 계획을 위한 정보로 제공하며 추정치만으로 전체 적재를 금지하지 않는다. 실제 여유 공간이 최소 운영 여유보다 작으면 증설·경로 변경 후 재개할 수 있도록 처리한다.
- 저장장치의 전체 용량, 현재 여유 공간, 원본 위치, DB 위치, 임시 공간 위치를 구분해 보여준다. 동일 볼륨의 여유 공간을 여러 경로에 중복 배정하지 않는다.
- HDD 환경은 순차 읽기와 배치 쓰기를 우선하고 초기에는 가져오기와 무거운 조회를 직렬화한다. 여러 파일을 무제한 병렬 읽기하지 않는다.
- 선택 가져오기는 사용자가 분석 범위를 좁히고 싶을 때의 후속 기능으로 둔다. 80GB에 맞추기 위해 데이터나 상세 정보를 자동 제외하지 않는다. 명시적으로 제외한 데이터가 필요해지면 원본 재스캔이 필요하다.
- 요약도 고유 IP/경로가 많으면 커질 수 있으므로 무제한 메모리 집계를 하지 않는다. 집계 상태에도 한도와 디스크 사용 정책이 필요하다.
- 원문 미저장이 확정 정책이다. 저장 필드 조회·재구성은 원본 없이 가능하지만, 실패행 확인과 재파싱에는 원본이 필요하다. 원본 재연결 시 파일 식별 정보를 검증한다. 원본 읽기 기능은 자동 전체 재스캔하지 않는다.
- 파서 버퍼, 대기 큐, DB 메모리 설정, 결과 버퍼, UI 캐시를 각각 제한하고 프로세스 전체 RSS도 측정한다.
- DuckDB memory_limit는 프로세스 전체의 강제 메모리 상한이 아니다. 결과 수집과 별도 할당량을 포함해 여유를 둔다.
- 동시 무거운 쿼리는 초기 1개를 기본으로 실험한다. 가져오기와 조회가 디스크·CPU를 경쟁할 때 작업량을 제한한다.
- 임시 디렉터리, 임시 파일 최대 용량, 최소 잔여 디스크 공간을 설정하고 부족 시 오류로 종료한다.
- 요구 공간은 사용자가 별도로 보유한 원본 + 분석 DB + WAL + 쿼리 임시 공간 + 재파싱/백업 여유를 합산한다. 고정 압축률을 약속하지 않는다.
- DB 연결만 열었다고 100GB 전체를 메모리에 올리지 않는다. 단, 쿼리별 중간 결과와 엔진 한계로 메모리 부족은 발생할 수 있다.

### 검증 기준

- 1GB → 10GB → 100GB 이상 단계로 같은 쿼리 세트를 측정한다.
- 처리량, 전체 RSS, 임시 공간 최고치, DB 크기, 첫 페이지 지연, 후속 페이지 지연, 전체 검색 시간을 기록한다.
- 순서가 섞인 시간 데이터, 긴 원문, 많은 고유 IP/경로, 압축 로그를 포함한다.
- 가져오기와 조회 동시 실행, 강제 종료 후 재개, 디스크 부족, 재구성 상세 조회와 출처 추적도 검증한다.
- RAM·저장장치 종류·압축 전후 용량을 기록해 결과를 재현할 수 있게 한다.
