# 선행 실험 벤치마크

1단계(엔진 선행 실험) 측정 기록. 확정 성능 목표가 아니라 배치·메모리 설정을 정하기 위한 기준값이다.
**기준 환경(Windows x64 / RAM 16GB / HDD)에서는 아직 측정하지 않았다.** 아래는 개발용 Mac 측정이며 CPU·SSD 차이로 Windows/HDD에서는 더 느릴 수 있다.

## 측정 장비

| 항목 | 값 |
|---|---|
| 기기 | Apple M1, RAM 16GB, 내장 SSD(APFS) |
| OS | macOS (Darwin 25.6) |
| Rust | 1.97.1 stable, `--release` (`debug = 1`) |
| DuckDB | duckdb crate 1.10505.0, `bundled` |
| 측정일 | 2026-09-07 |

RSS는 `/usr/bin/time -l`의 maximum resident set size(프로세스 전체)다. Windows에서는 `Get-Process`의 PeakWorkingSet64로 대체한다.
조회 지연은 각 조건마다 새 프로세스로 실행했다(DuckDB 버퍼는 cold, OS 파일 캐시는 직전 가져오기 때문에 warm일 수 있음).

## 데이터

`weblog gen`으로 만든 합성 Combined 로그. 같은 줄 복사가 아니라 고유 IP(IPv6 5% 포함)·경로(쿼리 문자열 포함)·UA 풀에서 뽑고, 5%의 줄은 최대 60초 늦게 기록된 것처럼 시간이 뒤섞인다. 0.5%는 깨진 줄, 0.1%는 빈 줄.

| 이름 | 줄 수 | 플레인 | gzip | 고유 IP / 경로 |
|---|---|---|---|---|
| combined_1g | 6,000,000 | 1,015 MiB | 133 MiB (7.6:1) | 200,000 / 50,000 |
| combined_10g | 60,000,000 | 10,155 MiB | (미생성) | 1,000,000 / 200,000 |

재현: `scripts/bench-run.sh` (전체, 약 8분) 또는 `scripts/bench.sh <lines> [gzip]`. 원본 출력은 `bench-data/results.txt`(git 제외).

## 가져오기

| 실험 | 설정 | 실시간 | 줄/초 | 논리 MB/초 | 피크 RSS | DB 크기 | 배치 수 | 읽기+파싱 | 커밋 |
|---|---|---|---|---|---|---|---|---|---|
| plain_1g | 기본(배치 50,000행/32MiB, DuckDB 기본 메모리·스레드) | 25.4s | 236k | 41.9 | 922 MiB | 144 MiB | 120 | 9.9s | 14.8s |
| gz_1g | 위와 같음, gzip 입력 | 26.8s | 224k | 39.8 | 943 MiB | 143 MiB | 120 | 11.3s | 14.8s |
| limited_1g | memory_limit 512MB, threads 2, 배치 20,000행 | 26.4s | 228k | 40.4 | 482 MiB | 145 MiB | 300 | 9.9s | 15.8s |
| plain_10g | memory_limit 2GB, threads 4 | 257.3s | 233k | 41.4 | 1,139 MiB | 1,397 MiB | 1,200 | 100.5s | 150.3s |

공통: 1GB 기준 레코드 5,964,046 / 오류 30,009 / 제외 5,945. 10GB 기준 59,640,215 / 299,779 / 60,006. gzip과 플레인의 결과 건수는 동일하다.

관찰:
- 처리량은 1GB와 10GB에서 거의 같다(약 235k줄/초, 42MB/초). 10GB에서 선형으로 늘어난 것 외에 둔화는 없었다.
- **병목은 DuckDB 커밋(Appender + 트랜잭션)** 으로 전체의 58~60%다. 읽기+정규식 파싱은 40%. 파이프라인이 단일 스레드 순차이므로, 파싱과 커밋을 겹치면(파서 스레드 → 제한 큐 → 쓰기 스레드) 이론상 최대 1.7배까지 줄일 수 있다. 3단계 이전에 적용을 검토한다.
- gzip 스트리밍 해제 비용은 1GB당 약 1.4초로 작다. 압축 입력을 기본으로 두어도 무방하다.
- DB 크기는 논리 입력의 약 14%(1GB → 144MiB, 10GB → 1,397MiB). 압축 후 100GB(≈760GB 논리)라면 **DB만 약 105GB 이상**이 필요하다. 압축률은 합성 데이터 기준이며 실제 로그의 고유값 분포에 따라 달라진다. 보장값이 아니다.
- 피크 RSS는 DuckDB memory_limit에 지배된다. 기본값(RAM의 80%)에서는 922MiB까지 썼고, 512MB로 제한하면 482MiB로 내려가며 속도 손실은 없었다. 파서·배치 버퍼 자체는 작다(배치 32MiB 상한).
- 배치 크기 20,000행(300배치)과 50,000행(120배치)의 처리량 차이는 4% 이내다. 200,000행(30배치)은 앞선 단발 실험에서 22.2s로 약 12% 빨랐으나 RSS가 1.6GB로 커졌다.

**초기 설정 결정(3단계 UI 기본값)**: 배치 50,000행 / 32MiB, DuckDB memory_limit 1GB, threads = 물리 코어 절반(최소 2). Windows/HDD 측정 후 조정한다.

## 조회 (페이지 크기 200, 3페이지, 커서 이동)

지연은 ms. `[첫 페이지, 다음, 다음]`. count는 별도 요청의 전체 건수 계산.

| 조건 | 1GB (596만 행) | 10GB (5,964만 행) |
|---|---|---|
| 시간 오름차순 전체 | 20.6, 14.7, 12.2 | 23.1, 12.0, 11.6 |
| 시간 내림차순 전체 | 33.5, 29.5, 25.2 | 30.4, 25.5, 25.3 |
| status = 500 | 5.9, 6.6, 6.1 (count 119,417: 5.1) | 9.7, 10.8, 4.9 (count 1,191,153: 42.0) |
| status 4xx | 6.2, 3.4, 3.9 | 10.4, 3.5, 2.6 |
| 시간 범위 1시간 | 2.5, 1.5, 1.4 (count 3,544: 0.4) | 6.4, 1.6, 1.4 (count 3,572: 0.5) |
| request_target 포함 검색 | 19.8, 84.3, 69.9 (count 10,231: 60.6) | 22.5, 148.8, 128.3 (count 91,763: 600.4) |
| client_ip 일치 | 32.7 (29행, count 25.6) | 315.5 (0행, count 240.2) |
| method=POST AND status=404 | 5.5, 14.4, 7.2 (count 43,232: 4.8) | 11.3, 9.0, 7.2 (count 429,580: 46.9) |
| 페이지 1000행 × 5 | 14.1, 15.1, 12.9, 13.6, 13.4 | 18.6, 12.8, 13.7, 13.8, 12.0 |
| 내림차순, memory_limit 512MB threads 2 | 25.0, 24.4, 24.0 | 28.9, 24.5, 24.2 |
| 포함 검색, memory_limit 512MB threads 2 | 14.5, 77.4, 73.1 (count 159.4) | 20.4, 90.5, 85.6 (count 1,602) |

관찰:
- 시간 정렬·타입 컬럼 필터·시간 범위는 10GB에서도 페이지당 수십 ms 이내다. DuckDB가 컬럼 zonemap으로 시간 범위를 건너뛰는 덕이 크다(시간 범위 조회는 1GB와 10GB가 같다).
- 문자열 포함 검색과 IP 일치 검색은 전체 스캔이며 데이터 크기에 비례해 늘어난다(10GB: 페이지 130~150ms, count 0.6초, 메모리 제한 시 1.6초). 100GB에서는 count가 수십 초가 될 수 있으므로 설계대로 **건수는 별도·취소 가능 작업**으로 두고, IP 조회가 핵심이면 후속 인덱스/전문 검색을 검토한다.
- 다음 페이지 지연이 첫 페이지보다 작거나 같다. 커서(timestamp, source_id, line_number) 키셋 방식이 OFFSET 없이 동작함을 확인했다. 단, 커서 조건은 정렬 컬럼 zonemap에 의존하므로 시간이 심하게 뒤섞인 데이터에서는 재측정이 필요하다.
- 첫 페이지 지연에는 DB 열기·메타데이터 읽기가 포함된다(각 조건 새 프로세스). 앱에서는 연결을 유지하므로 더 짧다.

## 정확성·보존 검증(같은 실행에서 확인)

- fixture 6종(Combined, Common, W3C 헤더 변경, 헤더 없는 W3C, 커스텀 파이프, BOM/CRLF)의 파서 출력과 DB 결과가 손으로 쓴 예상 결과와 일치(`crates/weblog-engine/tests/fixtures.rs`).
- gzip 입력과 플레인 입력의 파서 결과 동일.
- Appender로 넣은 행이 명시적 트랜잭션 ROLLBACK에 함께 되돌아감(장애 주입 테스트). 같은 (job, source, batch_seq) 재커밋은 중복을 만들지 않음.
- 1GB DB 파일 안에 원문 첫 줄이 통째로 존재하지 않음(바이트 검색). 스키마에 raw 계열 컬럼 없음.

## 미검증

- Windows x64, HDD, 한글/긴 경로. 위 수치는 SSD 기준이며 HDD에서는 커밋 비중이 더 커질 가능성이 높다.
- 압축 후 100GB. 10GB까지 선형이었고 DB 크기 추정만 제공한다. 100GB 실제 측정 전까지 처리 속도를 약속하지 않는다.
- 가져오기와 조회 동시 실행, 강제 종료 후 재개(2단계), 디스크 부족 시 동작.
- 임시 디렉터리 최고 사용량(정렬이 memory_limit을 넘는 조회를 아직 만들지 않음).
- 실제 서비스 로그의 고유값 분포·UA 길이에 따른 DB 크기 변화.

## 5단계: 통계·내보내기 (2026-09-08, 같은 Mac, release 빌드)

DB는 위 1GB(plain, 596만 행)와 10GB(plain10, 5,964만 행)를 그대로 썼다. 각 항목은 새 프로세스로 실행했다(DuckDB 버퍼 cold).

| 항목 | 1GB DB | 10GB DB (memory_limit 2GB, threads 4) |
|---|---|---|
| 통계 전체(건수·NULL·범위, 상태·메서드 분포, 상위 10 IP·경로, 시간축) | 0.54s | 7.4s |
| 통계, 하루 범위(86,260행) | – | 0.08s |
| 내보내기 CSV, status=500 (1,191,153행, 223MB) | – | 7.9s · 151k행/초 |
| 내보내기 JSON Lines, 전체(5,964,046행, 2.27GB) | 109s · 55k행/초 · 20.8MB/초 | – |

관찰:
- 통계는 조건 안의 전체 스캔이다. 10GB 전체 7.4초, 시간 범위를 좁히면 zonemap으로 0.1초 이하다. 100GB 전체 통계는 1분 이상이 될 수 있으므로 화면에서 시간 범위를 먼저 고르게 하고 중단 버튼을 둔다. 통계 결과의 상위 N·버킷 수는 상한이 있어 결과 크기는 데이터 크기와 무관하다.
- 내보내기는 커서 페이지(10,000행)를 디스크로 흘려보낸다. 페이지를 1,000행에서 10,000행으로 키우자 10GB 필터 내보내기가 21.9초에서 7.9초로 줄었다(커서 재조회 횟수가 병목). 전체 JSON Lines는 직렬화가 병목이라 55k행/초에 머문다. 원본 1GB → JSON 2.27GB로 부풀므로 대용량은 CSV나 조건 지정을 권한다.
- 내보내기 중 프로세스 RSS는 측정하지 않았다. 페이지 단위로만 메모리를 쓰므로 데이터 크기에 비례해 커지지 않는다(설계상). 필요하면 `/usr/bin/time -l ./target/release/weblog export ...`로 잰다.
